# 12｜产品优化建议（Agent 产品 · 银行专家版）

- 版本：v2（v1 基于"个人自用"的错误前提，已整体作废，由本版替代）
- 前提：**必须做成 Agent 产品；目标用户为银行/持牌机构的风控建模专家**；本地优先的数据安全边界不变
- 与 11 号文档的关系：11 审的是文档一致性（仍然有效，其中 P0 问题照常要修）；本篇回答"在 Agent 产品定位下，这套设计哪里做得不好、怎么优化才能成为专家愿意用于真实工作的产品"
- 日期：2026-08-20

## 0. 先定义"完美"

对银行风控专家，"完美"的 Agent 产品要同时做到四条：

1. **结果可信**：每一个数字、每一次排除、每一个建议都可追溯、可复现，专家敢拿它去做评审材料；
2. **比专家手工快**：把画像、泄漏排查、筛选、比较、报告撰写这些重复劳动压缩到小时级；
3. **像资深同事而不是黑盒**：Agent 给建议必附证据，专家可以直接改、直接否决，且改动被完整记录；
4. **数据不出本机是硬事实**：不是承诺，是专家（及其信息科技部门）可以亲自验证的机制。

Agent 架构本身不是问题——**问题在于这套设计把 Agent 的价值点放错了位置，把实施顺序排反了，并且漏掉了银行专家日常工作里最核心的几件事**。

## 1. 总体判断

方向上是对的，而且有三点应该明确肯定：

- **LLM 只做语义、Worker 做确定性计算**的分工，是 Agent 产品在银行场景唯一能站住脚的形态；
- **Reviewer 独立审核 + 审计留痕**与银行模型治理（模型开发、独立验证、文档化）的要求天然对齐，这是竞争壁垒而不是成本；
- **冻结方案 → 不可变产物 → 失效链**解决了 Agent 产品最被诟病的"不可复现"问题。

但按当前设计实施，会得到一个"架构完整、专家不爱用"的产品。以下逐条说明。

## 2. 做得不好的地方（按对产品成败的影响排序）

### 2.1 价值排序错位：把代码生成当核心，把报告撰写当配角

文档把 Code Agent + 三轮修复闭环放在很重的地位（03 §3.3、04 §10、10 Phase 4），而报告生成只是一个确定性模板工具 `render_report`（04 §5、07 §11）。

但银行建模专家时间消耗的真实分布大致是：**写报告和评审材料 > 反复迭代变量与口径 > 调参训练 > 写代码**。专家自己就会写代码（或有专门的开发支持），代码生成对他们是锦上添花；而"把一次完整建模写成 16 章评审级报告"是最枯燥、最耗时、最无人愿意做的部分。

**优化**：
- 把 `render_report` 从"确定性模板渲染"升级为 **Agent 驱动的报告叙事生成**：表格、指标、图由确定性产物来（保持单一数据源），但每章的**文字叙述**（数据质量结论、筛选理由、模型比较解读、局限性说明）由 Agent 基于产物证据起草，专家在页面上逐段审阅、修改、锁定，锁定后的报告参与哈希。
- Code Agent 降级到 P1 后段（见 2.9），把省下的工程量投给报告与迭代能力。

### 2.2 缺失：与存量冠军模型的比较——银行建模的日常起点

全部文档假设的流程是"从零建一个新模型"。但银行专家的真实任务几乎都是：**新模型必须和现行生产模型（冠军模型）比较**——在同样的样本上比 KS/AUC，做 swap set 分析（新旧模型各自拒绝的人群差异、通过率固定下的坏账捕获差异），回答"换模型能带来什么"。

现在的 `compare_models` 只在本次候选集合内比较（04 §5、07 §6），**没有"导入一个既有模型/既有评分列作为基线"的概念**。对一个要说服模型管理委员会换模型的用户，这是致命缺口。

**优化**：
- 新增一等公民对象 `BaselineModel`：可以是导入的评分列（CSV 一列分数）或一个模型文件 + 预处理；
- `compare_models` 与报告第 10、11 章支持"候选 vs 基线"：同分区指标对比、swap set（在给定通过率下新旧模型的坏账捕获矩阵）、分数分布漂移；
- 07 §7 指标表补充"固定通过率下的 Lift/捕获率"（专家按审批通过率思考，不按 0.5 阈值思考）。

### 2.3 缺失：快速 what-if 迭代——专家一天要改几十次口径

文档的世界观是"冻结方案 → 一次 Run"，修改意味着走失效链、生成新版本、重跑。这对**正确性**是对的，但对**体验**是灾难：专家的日常工作流是"把这个变量踢掉看看""OOT 改成去年 4 季度试试""缺失率阈值从 70% 放宽到 80% 呢"——每次都要等完整流程，产品就会被弃用。

02 §3 流程图里"派生新方案"只出现了一次且无任何细节。

**优化**：
- 把"派生方案版本"做成一键动作：从当前方案 fork，只重算受影响阶段（依赖图裁剪，02 §8 的失效规则正好反过来用——失效边界就是可复用缓存的边界）；
- 区分**正式 Run**（走完整审核、进报告）与**实验 Run**（快速、轻量、默认不进正式报告，可一键转正）。专家 90% 的操作是实验 Run，产品必须让实验 Run 在分钟级返回；
- 实验 Run 的结果页明确水印"实验结果，未审核"，与正式产物视觉区隔——既快又不破坏 07 的一致性纪律。

### 2.4 交互主客颠倒：专家需要"直接操作为主，Agent 建议为辅"

06 的设计整体是"Agent 提建议 → 专家确认"的流。对新手友好，对专家低效。银行专家知道自己要什么，他们需要的是：

- 直接在变量表里勾选排除/保留、直接改分箱边界、直接指定切分点，**改完立即看到影响**；
- Agent 在旁边说"你把 `beh_3` 踢掉了，注意它 IV 0.41 且与 `beh_7` 相关性 0.83，踢掉后建议关注 `beh_7` 的单调性"——**建议跟随操作，而不是操作跟随建议**。

现有确认卡机制（02 §7、06 §10）保留给高风险动作（改 Y、改窗口、删除样本），常规操作应是直接操作 + 即时反馈 + 事后可审计。

**优化**：06 增加"专家直操"原则：所有 Agent 可建议的动作，都必须有不经过 Agent 的直接入口；Agent 建议与专家直操产生同一种 Decision 记录，审计上无差别。

### 2.5 缺失：数据字典接入——银行宽表自带语义，要用起来

银行特征宽表有强命名规范（如 `qry_`=征信查询类、`beh_`=行为类、`loan_`=贷后类），且通常伴随数据字典（字段中文名、口径、来源表）。现在的字段别名机制（05 §2）只服务于脱敏，是"防它"而不是"用它"。

**优化**：
- 支持导入数据字典（XLSX/CSV：字段名 → 中文名、口径、类别），画像、变量表、报告全程显示中文名 + 口径；
- 泄漏检测规则（04 `detect_data_issues`）支持**按前缀/正则配置高危规则**：例如项目级配置"前缀 `loan_` 且无明确可用时间戳 → 高置信贷后泄漏"。08 AC-006 已要求不要只凭"逾期"二字误判——前缀 + 角色 + 用户证据的组合规则正是答案，且应由专家按本行命名规范配置，而非产品硬编码；
- 数据字典同时喂给 Agent：LLM 看到"中文名 + 口径"后，建议质量会显著高于看 `f_001`。注意：字典本身也走白名单判断（口径描述可能敏感，默认别名化，专家可选择性放开）。

### 2.6 Agent 产品却没有最小评测门禁——Prompt/模型一改，行为悄悄漂移

10 号文档把整个评测 Harness 后置（Phase 6）。对平台级评测这是对的，但 **Agent 产品裸奔到 V1 发布是危险的**：供应商模型升级、Prompt 微调，都可能让"Agent 是否还会拦住泄漏字段"这种关键行为无声退化，而银行场景无法接受"上周还拦、这周不拦"。

**优化**：不需要 Harness 平台，只需要最小回归集——

- 建 3—5 个**黄金用例**（合成数据 + 预埋问题：一个贷后泄漏字段、一个 Y 含 -1、一个训练集外拟合的代码缺陷）；
- 一条 CI 命令：用当前 Prompt/模型配置跑这些用例，断言关键行为（泄漏被 block、Y 异常被 block、Reviewer 对种子缺陷给出 block）；
- 断言只查**结构化输出**（verdict、finding code），不查自由文本，稳定且便宜；
- 09 号文档的 Trace 设计已完全支持这件事，等于白捡。把这个最小回归集列入 10 Phase 2 退出条件。

### 2.7 多 Agent 的延迟与成本没有工程对策

专家不会接受每个节点等 3 分钟。当前设计里主 Agent、分析 Agent、Reviewer 串行往返，一个带修复的完整 Run 可能是几十次 LLM 调用。文档只在 03 §7 支持"主/Reviewer 两个模型位"，没有任务级策略。

**优化**：
- 引入**任务级模型路由**：分类性质的任务（Y 候选识别、字段角色判断）用便宜快的模型，规划与审核用强模型；路由表本身版本化；
- **证据解释缓存**：同一数据版本 + 同一画像产物，解释只生成一次；what-if 迭代时大部分上游解释可复用；
- 全程流式（02/06 已有要求）+ 每个 LLM 阶段显示"正在审核代码（约 40 秒）"级别的预期，专家对延迟的容忍度主要来自可预期性；
- 单次 Run 的 token/费用预算与告警（11 号审计 P1-2 仍适用，对机构用户同样是采购关切）。

### 2.8 生成代码的定位要改为"交付物"，V1 砍掉执行基础设施

文档为"未来执行生成代码"设计了六重门禁（04 §10：AST 白名单、受限进程、一致性检查……）。但对银行用户，**他们的环境规范大概率根本不允许在本机执行 AI 生成的训练代码**；代码的真实用途是：导出给专家审阅、存入模型档案、供开发团队在生产环境复现。

**优化**：
- V1 明确"生成代码 = 交付物，不在产品内执行"。08 §3 的硬门禁"危险生成代码可执行"因此变成"危险生成代码**不会被执行**"——静态 AST 检查保留（它同时服务于代码质量审核），受限进程执行、合成数据执行测试、与 Worker 的一致性执行检查全部移出 V1；
- 这砍掉一整块最难的安全工程，同时更符合银行实际。若未来确有执行需求，再按 04 §10 的清单立项。

### 2.9 实施顺序仍然排反了（承接 11 号审计）

即使是 Agent 产品，Phase 1 也不该是"空壳大游行"（状态图、Trace Store、Tool Registry、Gateway 空壳）。正确顺序是：

1. 确定性管线先站立（它单独就有价值，且是所有 Agent 能力的地基）；
2. 安全边界（白名单 SafeEvidence）与管线同期——这是银行场景的准入资格，不是后置项；
3. Agent 层逐个节点叠加，每加一个立刻用黄金用例验证。

见第 4 节的重排路线。

### 2.10 安全边界应该被"看见"：出站载荷检查器

"原始数据不出本机"目前是专家只能**相信**的承诺。优化成可以**亲自查验**的功能：

- 设置页/项目记录页提供"出站请求日志"：每次 LLM 调用的完整出站 payload（已脱敏后的真实内容）、时间、用途、命中的策略版本；
- 专家或信息科技人员可以逐条翻阅、导出、抽验——**把合规焦虑转化为产品信任，这是银行场景最强的差异化能力**，而实现成本只是一个只读查看页（日志本来就要记，05 §10）。

### 2.11 补一个轻量但高频的流程：既有模型在新 OOT 上的复评

银行按季/按年用新时间窗数据复评存量模型（不是监控，是例行验证）。当前所有流程都从"建新模型"开始。建议 V1.x 支持：选定一个已完成的 Run（或导入的基线模型）+ 导入新数据版本 → 仅重跑评估节点 → 产出复评报告。这在 02 的状态机里是一条短路径（跳过计划/筛选/训练），成本低、对专家价值高。

## 3. 要保留并强化的（不要动）

| 保留项 | 说明 |
|---|---|
| Worker 确定性计算 + 工具白名单 | 产品的地基，一行不让步 |
| 不可变产物、哈希、run-manifest、失效链 | 复现与审计的全部根基；2.3 的实验 Run 也靠它 |
| Reviewer 独立审核 + 结构化 findings | 对齐银行模型治理；输出要作为**评审材料附件**优化格式 |
| Y 契约、泄漏、train-only 拟合等硬阻断 | 保留且永不因模式关闭 |
| SQLite 事实源、checkpoint 恢复 | 长任务体验底线 |
| 双运行模式 | 机构用户确实两者都需要（试点期半信任、熟手自动），保留；11 号审计 P1-6 的切换语义照常要补 |
| 报告状态机（Draft/Validated/Superseded/Invalid） | 与评审流程契合 |
| "未发现阻断问题"式措辞纪律 | 在银行场景尤其正确 |

## 4. 优化后的实施路线（每步产出可演示的 Agent 能力）

| 步骤 | 内容 | 完成标志 |
|---|---|---|
| Step 0 确定性管线 | 导入 → 画像 → Y 契约 → 泄漏/基础筛查 → IV/单变量筛选 → 切分 → LR 评分卡 + XGBoost → 比较 → 报告骨架；同期建立白名单 SafeEvidence 与出站日志 | 一条命令跑通合成 + 真实脱敏数据，报告数字全部可溯源 |
| Step 1 主 Agent 上身 | 证据解读、Y/切分/筛选建议 + 证据引用；确认卡闭环（半信任模式）；黄金用例回归集进 CI | 专家采纳/否决建议的操作全部留痕；3 个黄金用例通过 |
| Step 2 Reviewer 上身 | 计划审核 + 代码/方案审核，结构化 findings，修复闭环（保留三轮上限） | 种子泄漏/偷看问题 100% 触发 block |
| Step 3 对话与钻取 | 对任意证据提问；自然语言 → AnalysisSpec → 1—4 维分析（含小样本抑制） | 专家可用对话完成一次完整的异常追查 |
| Step 4 报告叙事生成 | Agent 起草各章文字，专家逐段改定锁定，报告参与哈希 | 一份可直接用于内部评审的报告 |
| Step 5 what-if 与基线 | 实验 Run、方案 fork、BaselineModel 与 swap set、既有模型复评短路径 | 一次"踢变量看影响"迭代在分钟级完成 |
| Step 6 Code Agent | 交付物导向的代码生成 + AST 检查 + Reviewer 审代码（不执行） | 导出代码可在专家自己的环境复现本次 Run |
| 并行 | 出站载荷检查器、任务级模型路由、费用预算 | 随对应步骤落地 |

注意与原路线图的差异：**代码生成从 Phase 4 的核心位置移到 Step 6；报告叙事、what-if、基线比较这三件"专家真正天天干的事"从无到有进入路线**；跨平台打包与桌面壳维持后置（若机构统一部署，Web 本地服务形态已经够用，桌面壳等真实需求出现再立项）。

## 5. 工程细节建议

1. **确定性配置**：LLM temperature=0、固定系统提示版本、结构化输出强制校验 + 有限重试（02 §11 已有错误分类，落实即可）；
2. **ID 与引用**：artifact 引用统一 `artifact://type/version` + 哈希双校验，避免 11 号审计 P0-4 类失效漏洞在实现层重演；
3. **状态模型**：按 11 号审计 P0-2 拆成项目级 × Run 级两层，再实现；
4. **前端**：银行专家是桌面宽屏用户，06 的三栏结构可以保留，但中间栏主内容应是**证据与表格**，Agent 时间线居右或可收起（对应 2.4）；
5. **数据字典与规则配置**：全部版本化、随项目导出，作为模型档案的一部分；
6. **XLSX 与编码**（11 号审计 P1-4 照常有效）：银行导出的 GBK/混合编码 CSV 很常见，导入层要做实；
7. **错误码注册表**（审计 P2-5）：机构用户的 IT 报障依赖稳定错误码，尽早建。

## 6. V1 完成定义（银行专家版）

用**一份真实脱敏的银行宽表**（或高度仿真的行内结构数据）验证：

- [ ] 全流程从导入走到评审级报告，专家只在关键节点做决策，不做搬运；
- [ ] 与一个既有冠军模型完成 swap set 比较，结论进报告；
- [ ] 一次 what-if 迭代（改一个筛选阈值）分钟级返回，且正式产物未被污染；
- [ ] 黄金用例回归全绿；Prompt 或模型版本变更后必须重跑方可发布；
- [ ] 出站载荷日志逐条可查，抽检零原始记录、零原始列名（审计 P0-5 的别名纪律已实现）；
- [ ] 报告从页面、HTML、XLSX、JSON 四个出口数字一致；
- [ ] 刷新、重启、取消后状态恢复正确；
- [ ] 专家用自己的老项目手工结果与本工具对账：指标一致、筛选结论可解释。

全部打勾，才是"银行专家可用的 Agent 产品 V1"。

## 7. 三条纪律

1. **真实结构数据驱动**：第一周就用行内结构的宽表（可脱敏合成，但列数、命名、脏法要像真的）。合成"玩具数据"只能验证管线，验证不了产品。
2. **每个 Step 结束必须有一次真演示**：对着真实数据向一位真实建模专家演示。他说"这个我用得上"才进入下一步。
3. **文档冻结**：11、12 两份意见消化完后，docs/ 进入"代码发现错误才允许改"的只读期。文档已经超前于实现太远，继续迭代会持续消耗本应写代码的精力。

## 8. 结语

这套设计的骨架——Agent 编排、独立审核、确定性兜底、数据不出本机——对银行专家场景是**正确的骨架**，市面上多数"AI 建模"产品恰恰缺这些。真正的风险不在架构，在于实施时会不自觉地把工程量花在"让架构完整"上，而不是"让专家的一天变快"上。

判断每个迭代值不值的标准只有一个：**银行建模专家会不会用它做下一个真实项目，并敢把产出的报告提交评审**。2.1—2.5 的五个缺口（报告叙事、基线比较、what-if 迭代、直接操作、数据字典）就是"敢"与"不敢"之间的全部距离。
