# 10｜研发路线图与 Backlog

- 文档版本：v1.0
- 日期：2026-08-20
- 目标：把产品合同拆成可验证、可提交、可回滚的实施顺序

## 1. 实施原则

1. 先冻结合约，再实现功能。
2. 先做一条完整垂直闭环，再扩展所有算法和页面。
3. LLM 语义与确定性计算分离。
4. 原始数据安全边界和本地确定性管线先于外部 API 接入。
5. 状态、Trace 和失效规则从第一条链路开始实现。
6. 普通软件测试与功能同步；独立评测 Harness 后置。
7. macOS 与 Windows 分别验证，不从开发机结果推断另一个平台。
8. 每个阶段使用独立、相关的 Git 提交，并保持工作树清晰。

## 2. 技术基线

目标技术选择：

- Python 3.11；
- FastAPI 本地服务；
- LangGraph 编排；
- SQLite 领域状态与本地 checkpoint；
- 外部 OpenAI-compatible Provider Gateway；
- pandas/Polars/DuckDB 按数据规模选用；
- scikit-learn、XGBoost；
- Web 前端，桌面壳在核心稳定后确定 Tauri 等方案；
- SSE 或 WebSocket 事件流；
- Pytest、Ruff、类型检查和前端测试。

选择锁定前需完成依赖许可、Python 版本、跨平台 Wheel 和打包可行性检查。

## 11. 关键风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| LangGraph 与现有 Python 版本不兼容 | 无法安装 | 统一 Python 3.11 并锁版本 |
| XGBoost 跨平台依赖 | 安装包失败 | 早期做 Mac/Windows Wheel 冒烟 |
| LLM 输出不稳定 | 流程漂移 | 结构化 Schema、有限重试、Mock 测试 |
| Reviewer 与主模型错误相关 | 漏审 | 支持独立模型，确定性门禁兜底 |
| 2 万字段超内存 | 崩溃 | 分阶段/分块、资源预测和限制 |
| 多维分析组合爆炸 | 页面和内存不可用 | Top-K、分箱、小样本与最大组合 |
| 原始数据意外外发 | 严重安全事件 | Provider Gateway、DLP、测试和网络边界 |
| 过早做桌面打包 | 频繁返工 | 先锁服务边界，后做交付层 |
| 把测试指标当业务效果 | 误导 | 报告事实边界与证据标签 |

## 12. 研发决策记录

已确认：

- V1 只做二分类；
- 外部 LLM，不用本地 LLM；
- 原始数据本地；
- LangGraph 为编排运行时；
- Worker 工具化且不是 Agent；
- 主 Agent 与 Reviewer 结构化反馈循环；
- 双运行模式；
- 独立 Harness 后置；
- Web 工作台并最终打包 Mac/Windows。

待确认：

- 首个供应商与主/Reviewer 模型；
- 支持数据规模和安全阈值；
- 桌面壳与签名发布方式；
- 企业部署的日志保留、删除和备份策略。
