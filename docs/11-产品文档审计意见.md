# 11｜产品文档基线审计意见

- 审计对象：README.md、.gitignore、docs/01—10 全部产品文档
- 审计日期：2026-08-20
- 审计方式：逐文件通读 + 文档间交叉一致性核对 + Git 仓库状态核实
- 审计立场：以“研发即将以此文档集为实施合同”为前提，检查其是否足以作为冻结基线
- 严重级别定义：
  - **P0**：内部矛盾或架构级缺口，必须在 Phase 0 退出前解决；
  - **P1**：重要设计缺口，应在对应研发阶段开始前补齐；
  - **P2**：一致性、表述与工程细节建议，不阻塞开发。

## 1. 总体结论

这份文档集的**整体质量明显高于常见的产品基线**：安全边界用负向测试和硬门禁表达、确定性计算与 LLM 语义严格分离、产物不可变与版本化思想贯穿始终、措辞克制（统一使用“未发现阻断问题”而非“绝对安全”）、范围控制诚实（明确列出 V1 不做项与“尚未冻结项”）。作为需求基线，它已经具备较高的可实施性。

但按文档 10 §3 自己设定的 Phase 0 退出条件——“文档内部没有矛盾”——衡量，**当前尚未完全达标**。本次审计发现 6 处 P0 级矛盾或缺口（详见第 3 节），其中两处（Worker 执行模型、状态机归属）若带入实现阶段，会造成架构返工；另有一处（字段别名与代码文本外发）会直接削弱产品的核心安全承诺。建议在宣布 Phase 0 完成前逐项闭环。

## 2. 值得肯定的设计（保持）

1. **Worker 不是 Agent**、工具白名单 + 参数 Schema 服务端校验（04 §2、§5）——这是整个系统可控性的根基；
2. **安全承诺由代码和网络边界实现，不依赖 Prompt 自律**（05 §1），并以 AC-S01“原始记录外发负向测试”作为验收（08 §5）；
3. **发布硬门禁清单**（08 §3）把“不得宣称支持”“不得复用旧指标”等容易妥协的事项写成了不可绕过的条件；
4. **确认与点赞分离**、失效规则表、不可变产物版本链（02 §8、§9；03 §9）；
5. **“自动运行模式”命名决策**（01 FR-009）：拒绝“完全信任”作为正式名称，避免用户误以为安全约束关闭，这是一个少见的、正确的产品命名判断；
6. **评测 Harness 后置但 Trace 先行**（09）：范围决策理性，接口预留充分；
7. **跨平台“分别验收、不推断”**（08 §8；10 §8）与“支持规模测完再声明”（08 §6）。

## 3. P0 问题（阻塞 Phase 0 退出）

### P0-1 Worker 执行模型自相矛盾：进程内调用 vs 进程级隔离

- 位置：04 §2 vs 05 §7、04 §11
- 问题：04 §2 写“V1 优先使用**进程内**强类型调用或本地 JSON-RPC”；但 05 §7 对 Worker 的要求是“默认无网络、不继承不必要的环境变量和凭据、资源限制/超时/取消**由父进程控制**”，04 §11 也要求超时、取消、内存上限。这些都属于**进程级隔离能力，在进程内调用中无法强制执行**：进程内无法可靠杀死超时任务、无法限制内存、无法做网络隔离，一次 Worker 内存越界会直接拖垮主服务。
- 影响：若按“进程内”实现，05 §7 的安全与资源条款全部落空；若按子进程实现，04 §2 的表述误导实现者。
- 建议：明确分层——只读、低风险的纯统计类工具可进程内调用；凡涉及大数据量、训练或执行生成代码的工具，一律受控子进程（独立进程 + 资源限制 + 取消信号 + 目录沙箱）。把这条写入 04 §2 与 05 §7，并删除“进程内优先”的笼统表述。

### P0-2 “项目状态”表混入了 Run 级状态，且无迁移矩阵

- 位置：02 §4、§2
- 问题：§4 标题为“项目状态”，但 `training`、`validating`、`completed`、`failed`、`cancelled` 明显是 **Run 级**语义（`completed` 的含义原文即“本次 Run 成功完成”）；同时 02 §2 已把 Project 与 Run 定义为两个对象。此外 22 个状态为扁平枚举：`awaiting_confirmation` 与 `cleaning_review`（“待审核或确认”）语义重叠；没有状态迁移图/迁移表，无法判断哪些迁移合法。
- 影响：实现时 LangGraph 状态、领域状态、UI 状态三层各画一套，互相漂移；这也是 02 §10“崩溃恢复”正确性的前提。
- 建议：拆为两级——项目状态（draft / data_imported / active / completed / archived）× Run 状态（phase × status 组合），并补一张迁移矩阵或状态图作为 02 的正式内容；NodeRun 状态（§5）保持独立。

### P0-3 导入向导与状态机时序不一致

- 位置：06 §5 vs 02 §3、§4、§7
- 问题：06 §5 把“Y 候选（步骤三）”“样本切分（步骤四）”放进**导入向导**，即导入时一次完成；但 02 的状态机是：导入 → 画像（profiling/profile_ready）→ 主 Agent 计划 → Reviewer 审核 → 确认卡（Y 与样本、切分分别为第 1、2 类确认卡）。Y 候选卡片还要求展示“Agent 推荐理由”，而 Agent 理由依赖画像证据——向导步骤二只有“数据预检”，不足以支撑。
- 影响：前端按 06 实现会跳过 Agent/Reviewer 环节，或被迫推翻向导结构。
- 建议：把 06 §5 的向导限定为“文件选择 + 数据预检”两步；Y 选择与切分移到 `profile_ready` 之后的确认卡页面（与 02 §7 对齐），或在 02 中明确“向导内完成的是粗选，正式绑定发生在确认卡”。

### P0-4 失效规则表遗漏 Y 变化的上游依赖

- 位置：02 §8
- 问题：“Y 字段或 0/1 含义变化 → **样本切分之后**的全部内容失效”。但 `analyze_target`（Y 分布、类别检查）与画像中的 Y 相关统计发生在切分**之前**且直接依赖 Y，按此表不会被失效，会残留与新 Y 矛盾的证据。
- 影响：失效规则是 02 §1 原则 4 的落地依据，表不完整 = 行为不正确；此类手工枚举表每加一种产物就有漏一次的风险。
- 建议：短期补全表格（Y 变化同时失效目标分析与 Y 相关画像产物）；长期把失效改为**由产物依赖图自动推导**（每个 Artifact 声明 input_refs，失效 = 依赖闭包），把手工表降级为示例。09 §4 的事件结构已有 `input_refs/output_refs`，具备实现基础。

### P0-5 字段别名机制与“代码文本可外发”冲突，别名化可能形同虚设

- 位置：05 §2、§3、§4 vs 03 §3.3、08 AC-006
- 问题：05 §2 明确“字段名本身可能包含敏感含义”，要求别名化；但 05 §3 同时允许向外部 LLM 发送“代码文本和结构化方案”。Code Agent 生成的代码必然引用真实列名——08 AC-006 举的例子恰是 `post_loan_overdue_days` 这类**自带敏感语义的字段名**。若代码和方案按原名外发，别名机制在最敏感的位置失效。
- 影响：直接削弱“原始数据不上传”之外的第二层承诺（元数据最小化），且 DLP 测试（AC-S02）未必覆盖“代码中的列名”这一路径。
- 建议：规定**所有离开本机的代码与方案一律使用别名字段名**，本地 Worker 在执行入口做别名 → 原名的映射还原；在 AC-S01/AC-S02 中显式增加“外发代码与方案中不得出现原始列名”的断言。

### P0-6 “验证协议”被多处引用但从未定义

- 位置：04 §9、07 §6、08 AC-017（引用方）；04 §5 `train_candidate` 输出含 “OOF/验证结果”
- 问题：模型公平比较的核心前提是“同一验证协议”，三份文档反复引用该词，却没有任何一处定义它：调参用训练集内 K 折交叉验证还是单一验证集？“OOF”意味着 CV，而 01 FR-003 的切分只有 train/validation/OOT 三段，两者关系未说明；阈值选择发生在哪个分区也未规定（07 §7 只要求“阈值来源必须明确”）。
- 影响：这是 07 §6“公平比较要求”的第一块基石。不定义就无法实现，也无法验收 AC-017。
- 建议：在 07（或 04）中新增一节《验证协议》，冻结：调参仅在训练集内 CV、验证集用于候选比较与早停、OOT 仅在模型选择规则锁定后使用一次、阈值在验证集选择并固定后应用于 OOT。

## 4. P1 问题（应在对应阶段开始前解决）

### P1-1 银行内网/代理/LLM 不可用场景完全缺失

目标客户（银行、小贷、消金的风控建模人员）大量处于内网、代理、白名单出口环境。全部 10 份文档没有讨论：代理配置、企业 TLS 网关、连接失败的诊断，以及 **LLM 不可用时产品还能做什么**。而本产品最大的架构优势恰恰是 Worker 全确定性——应明确“无 LLM 降级路径”（例如：确定性流程仍可手动推进，Agent 环节显示不可用）。这是商业化阻塞级缺口，建议写入 01 风险节与 06 设置页，并在 Provider Gateway（05 §5）规格中加入代理与连通性自检。

### P1-2 LLM 成本/Token 预算没有上限与熔断

03 §6 只限制了修复轮次（三轮）；09 §4 事件里有 token/cost 字段但仅用于记录。一次完整 Run（多轮对话 + 计划 + 审核 + 代码生成 + 三轮修复）叠加 2 万字段场景，费用可能远超直觉，且 06 §17 设置页只有 CPU/内存预算。建议：在设置中加入单次 Run 与单月的 token/费用预算及触顶行为（降级为仅确定性流程 / 停止并要求确认），并把预算事件纳入 Trace。

### P1-3 凭据安全存储（Keychain/Credential Manager）排在 Phase 5，晚于真实 API 验证的需要

05 §6 要求 OS 级凭据存储，但对应 Backlog（P2-403/404）在 Phase 5 桌面交付阶段；而 SafeEvidence、DLP、Gateway 的行为必须在**真实供应商 API** 上尽早验证（真实 API 的超时、限流、结构化输出失败模式，Mock Provider 无法覆盖）。Phase 2—4 之间真实 Key 存哪里没有交代。建议把凭据存储提前到第一次真实接入之前（哪怕先做最简 OS keychain 封装），并在 10 中显式标注“首次真实供应商接入”的里程碑。

### P1-4 XLSX 导入的内存放大风险未专门对待

8GB 目标机上，openpyxl 类解析库对大 XLSX 的内存放大通常在 10 倍以上，极易在导入阶段直接失败——而 01 FR-002 与 06 §5 把 XLSX 列为 V1 必须。01 §11 又把“最大文件规模”列为未冻结。建议：明确 XLSX 采用流式/低内存解析（如 calamine 或 read-only 模式）、导入前基于文件大小做预拒绝并给出可理解提示；把“XLSX 与 CSV 分别的最大支持规模”尽早冻结（见 P1-5）。

### P1-5 “2 万字段”既是设计目标又是未冻结项

04 §8 以“支持 2 万字段和 8GB 内存”为前提设计分阶段筛选，01 §11 又把“最大行数/字段数”列为尚未冻结。架构（分块、DuckDB/Polars 选型、进度模型）都被这个数字驱动，它实际上已经是冻结需求。建议：01 §11 中将其移出“未冻结”清单，正式写为设计目标，并注明“支持规模声明以 08 §6 实测结果为准”。

### P1-6 同一项目的并发 Run、运行中切换模式的语义未定义

- 一个项目能否同时存在两个活动 Run？文档未说（建议显式规定：单活动 Run，新 Run 需取消或等待旧 Run 终结）。
- AC-013 允许“随时切换到人工处理”，但切换后：已排队的自动动作、正在等待的 `warn` 处理、已生成未确认的方案分别如何处置，02 §6 没有定义。建议补充“模式切换只影响后续决策点；当前节点按切换前语义完成或显式重新确认”。

### P1-7 模型序列化格式未定义

07 §12 列出“模型包”为必交付物，但未规定格式。pickle 有任意代码执行与跨版本不可复现问题，与产品“可复现、可审计”的定位冲突。建议：优先原生格式（XGBoost `save_model`、sklearn pipeline 记录依赖版本 + joblib 并声明加载策略），写入 07 §12，并在 05 §8 的危险模式中补充“加载不受信模型文件”。

### P1-8 类别不平衡处理缺失

风控场景坏样本率通常 1%—5%。FR-007、04 §9、07 §6 均未提及类别权重（`class_weight`、`scale_pos_weight`）或重采样策略（及其带来的泄漏注意事项）。建议作为“模型专属预处理”的一部分在 04 §9 明确：允许算法级不平衡处理、必须记录、且规则只在训练分区拟合。

### P1-9 项目数据的备份/迁移机制缺失

05 §9 定义了存储结构，05 §12 说明升级不删数据，但没有任何“项目导出/备份/换机迁移”的安排。建模项目（数据版本、方案、模型、审计链）是用户的核心资产，企业用户尤其会有此要求。建议加入 Backlog（P1 级）：项目级导出包（产物 + Manifest + 哈希，不含或可选含原始数据）与导入恢复。

### P1-10 间接标识符识别的难度需要在文档中降级表述

05 §4 步骤 2“识别直接和间接标识符”是业界未解决的难题（组合准标识符可再识别个体）。当前 min_group_size=50 的聚合抑制是正确的主力手段，但“识别间接标识符”不宜写成可完全做到的能力。建议表述为“基于保守规则（默认拒绝 + 名单 + 别名化）处理疑似标识符，不承诺穷尽识别”，与 05 §14“通过测试不等于合规认证”的诚实口径保持一致。
